# Calibration and Drift Engineering

## Principle

Calibration is a versioned evidence artifact, not a hidden startup step.

## Calibration classes

### Acquisition calibration
Validates:
- node/radio configuration;
- coefficient interpretation;
- timing behavior;
- expected frame rate;
- channel stability.

### Environment baseline
Captures:
- empty/static room behavior;
- static multipath baseline;
- per-link variance/noise;
- selected subcarrier quality.

### Geometry calibration
Captures:
- node/AP positions and orientations;
- room/world transform;
- reference-sensor extrinsics.

### Capability calibration
Examples:
- presence thresholds;
- respiration quality thresholds;
- localization model;
- confidence calibration.

Do not merge these into one opaque "calibration file."

## Calibration identity

Each calibration includes:
- ID/version;
- calibration type;
- environment ID;
- topology digest;
- sensor IDs;
- firmware/protocol versions;
- RF config;
- input capture IDs;
- algorithm version;
- quality/residual metrics;
- creation time;
- validity state;
- invalidation rules.

## Invalidation triggers

Potential hard invalidation:
- node/AP moved beyond tolerance;
- antenna changed/orientation changed;
- Wi-Fi channel/bandwidth changed;
- firmware changes CSI semantics;
- topology membership changes for a geometry-specific solver;
- room/environment ID changed.

Potential soft degradation:
- furniture/layout changed;
- temperature/power/RF background changed;
- slowly increasing residual/noise;
- packet-rate behavior changed.

## Drift detection

Monitor:
- baseline feature distribution;
- link variance/noise floor;
- residual between expected and observed static behavior;
- model confidence/rejection rate;
- false-trigger controls where available;
- topology health.

A drift detector produces evidence; it does not automatically prove the cause.

## Validity states

```text
VALID
DEGRADED
STALE
INVALID
UNKNOWN
```

Capabilities declare which states they accept.

Example:
- raw signal viewer may run with `UNKNOWN`;
- calibrated localization may require `VALID`;
- research mode may allow `DEGRADED` with explicit labeling.

## Recalibration UX

The operator UI should explain:
- why recalibration is requested;
- which capabilities are affected;
- what changed;
- required room state (e.g. empty);
- expected duration;
- resulting quality.

## QA

Test:
- moved node;
- changed channel;
- stale calibration;
- corrupted calibration artifact;
- wrong environment ID;
- partial-node topology;
- calibration generated by incompatible firmware/model.

The safest failure is capability withdrawal, not silent reuse.
